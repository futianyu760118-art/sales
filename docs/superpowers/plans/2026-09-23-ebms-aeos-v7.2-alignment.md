# EBMS AEOS V7.2 Alignment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze the M03 EBMS boundary and add a tested AEOS V1 contract/closure foundation without deleting or breaking existing business routes.

**Architecture:** Keep the current Node.js/Express/JSON application operational while adding a side-by-side `backend/aeos` boundary. Cross-domain legacy data is wrapped by an explicit registry and adapter; new M03 APIs only accept versioned contracts and store Decision/Action/Result/Evidence records in dedicated JSON tables.

**Tech Stack:** Node.js CommonJS, Express 4, built-in `node:test`, built-in `crypto`, existing JSON table layer, JSON Schema documents used as contract definitions.

**Spec:** `docs/superpowers/specs/2026-09-23-ebms-aeos-v7.2-alignment-design.md`

## Global Constraints

- Follow “先边界、后功能；先闭环、后扩展”.
- Do not delete or disable existing inquiries, customers, quotes, orders, R&D, procurement, finance, or IM routes in P0/P1.
- Do not migrate production JSON data to PostgreSQL in this plan.
- Authentication must continue to trust Bearer tokens only.
- New M03 endpoints must use AEOS V1 contracts and must not calculate professional-domain metrics.
- Missing evidence must produce `UNVERIFIED`, never a verified management result.
- Every new cross-domain read must be registered with source, consumer, purpose, contract version, owner, and deprecation condition.
- Every task ends with tests and one focused commit.

## Review Focus

1. A contract with missing, unknown, or malformed fields must fail with deterministic machine-readable errors and must not write data.
2. Duplicate events/actions with the same idempotency key must return the original record rather than create a second record.
3. A Result without evidence must remain `UNVERIFIED`; adding evidence may promote it only through an explicit verification operation.
4. Legacy records with missing fields must be marked `unknown` or rejected; adapters must never invent evidence.
5. Existing routes and Bearer-token authentication must remain operational when the AEOS feature flag is disabled.
