# EBMS 企业经营管理平台最新系统方案

> 版本：2026-08-15  
> 文档性质：当前代码基线、部署方案、运行边界与后续治理路线  
> 适用范围：项目根目录、实际运行目录 `frontend/` 和 `backend/`

## 1. 方案摘要

EBMS 是面向企业销售、研发、供应链、生产协同、质量、经营分析和组织权限管理的轻量级企业经营管理平台。当前系统采用“浏览器原生前端 + Node.js/Express 后端 + 本地 JSON 数据文件 + 外部业务接口”的单体架构，使用 Docker 统一运行，默认服务端口为 `3010`。

本版本的重点是让系统可持续运行和可验证交付：

- 统一实际运行目录的 UI 图标为本地 SVG，减少 Emoji、平台字体和尺寸漂移问题。
- 修复 AI 助手配置读取、外部请求和行动项返回链路。
- 为订单分析、物料看板等聚合查询增加短 TTL 内存缓存。
- 对本地 JSON 数据增加原子写入、表级写互斥、关键表备份和物料数据自愈。
- 通过 Docker 非 root 用户、健康检查、数据卷和重启策略形成可重复部署方案。
- 保留现有页面路由、API、权限码、业务字段和数据结构，不引入第三方图标 CDN。

## 2. 建设目标与边界

### 2.1 建设目标

1. 统一管理客户、询价、报价、订单、项目、物料、供应商和经营结果。
2. 通过订单分析和经营报告关联订单、BOM、物料、人工、费用和实际执行结果。
3. 让 AI 助手能够读取业务上下文、调用外部大模型并生成可跟踪行动项。
4. 建立部署、升级、数据备份、性能验证和故障排查的标准流程。

### 2.2 当前边界

- 不替换现有后端 API、数据库字段、页面路由和权限码。
- 实际运行源是根目录 `frontend/`；`frontend/frontend/` 是历史镜像，不作为本版本运行修改范围。
- 不在运行时依赖外部图标字体或 CDN。
- 不把企业 Memory、岗位 Agent、Skills Engine 和自动决策描述为当前已完成能力。
- 本地 JSON 方案适合单机/单容器，不等同于多实例事务数据库。

## 3. 总体架构

```text
浏览器
  │ HTTP / WebSocket
  ▼
Node.js 22 + Express
  ├─ /api/*                  业务 API 与权限校验
  ├─ /ws                     即时消息与数据变更通知
  └─ frontend/               原生 HTML / CSS / JavaScript
       │
       ├─ database/*.json    本地业务数据与运行时配置
       ├─ uploads/            上传文件
       └─ 外部系统接口        ERP/SPC、数据同步、AI 服务

Docker Compose
  ├─ sales-service-system 容器
  ├─ 3010:3010 端口映射
  ├─ ./database:/app/database
  └─ ./uploads:/app/uploads
```

| 层次 | 当前方案 |
| --- | --- |
| 前端 | 原生 HTML、CSS、JavaScript，无构建工具依赖 |
| 后端 | Node.js 22、Express 4、CORS、WebSocket `ws` |
| 数据 | 本地 JSON 表文件，由 `backend/db.js` 统一读写 |
| 导入导出 | `multer`、`xlsx`、PDF 相关库、浏览器打印/下载 |
| AI | OpenAI-compatible `/chat/completions` |
| 部署 | Dockerfile + Docker Compose，容器内非 root 运行 |

## 4. 业务功能地图

### 4.1 销售与客户经营

- 工作台：经营摘要、快捷入口、通知、待办和 AI 助手。
- 客户管理、客户附件、客户转移和客户来源。
- 询价管理、状态流转、客户同步和询价沟通。
- 核价、价格标准、产品配置、报价预览、打印和导出。
- 订单管理、订单产品、订单审核、订单检查和执行关联。
- 订单分析库：计划成本、同类订单差异、计划与实际成本、BOM 树、工价和审计。

### 4.2 研发、产品与工程

- 产品和产品配置、BOM、BOM 类型、BOM 差异、BOM 问题。
- 研发项目、年度经营计划、技术转移、规格书库和样品管理。
- SOP 产销协调会、稽核报告、部门报告和 Action 闭环。

### 4.3 供应链、物料与生产协同

- 物料库、物料成本、分类、库存、仓位和导入导出。
- 供应商、供应商评价、采购订单、采购申请和外部同步。
- 物料自检、物料问题、数据清洗和物料数据自愈。
- 人工费率、产品工价、生产协同和订单实际成本归集。

### 4.4 质量、经营与平台管理

- 质量/合规自检、规则、反馈和测试报告。
- 经营报表、工作台看板和数据导出。
- 用户、角色、权限、组织、岗位、数据范围和系统设置。
- AI 助手、聊天浮窗、即时消息中心和 WebSocket 通知。

## 5. 前端方案

### 5.1 公共 Shell

- `common.css`：全站布局、颜色、表格、弹窗、按钮、响应式和图标样式。
- `common.js`：公共导航、数据加载、通用交互和动态 DOM 处理。
- `permission-check.js`：页面权限与菜单过滤。
- `chat-widget.js`：AI 聊天浮窗、行动项展示和消息交互。
- `data-scope.js`：数据范围提示和加载。
- `icons.js`：本地 SVG 图标注册和挂载。

### 5.2 SVG 图标系统

`window.EBMSIcons` 提供 `render(name, options)`、`mount(root)` 和 `text(name)`。统一约束如下：

- `stroke="currentColor"`、`stroke-width="1.6"`、`fill="none"`。
- 不使用外部 CDN、Emoji 字体、渐变或平台相关字符图标。
- 尺寸 Token 为 `14px / 16px / 20px / 24px / 40px`，对应 `xs / sm / md / lg / xl`。
- 图标按钮保留 `aria-label` 或可读标题；纯装饰 SVG 使用 `aria-hidden`。
- MutationObserver 忽略已生成的 `<svg>`，防止递归挂载导致页面崩溃。

图标审计脚本 `scripts/audit-icons.js` 只扫描实际运行目录 `frontend/`，检查 Emoji、装饰性 Unicode、旧图标类名、非 Token 尺寸和缺少可访问名称的图标按钮。

## 6. 后端与数据方案

### 6.1 API 分组

后端通过 `/api` 汇总路由，主要包含 `inquiries`、`customers`、`products`、`materials`、`procurement`、`suppliers`、`orders`、`projects`、`pricing`、`quote`、`reports`、`permissions`、`settings`、`chat`、`ai-assistant`、`organization`、`data-scope`、`material-check`、`order-analysis`、`sop` 和 `im` 等。

各路由继续使用现有业务字段和权限码，聚合接口负责统一计算口径，避免前端拼接多个来源产生不一致。

### 6.2 权限模型

`backend/auth-middleware.js` 按用户 ID、角色、角色权限、岗位默认权限、岗位角色和人员级 grant/deny 合并权限。管理员拥有全部权限，业务路由通过 `requirePerm('module:action')` 或 `requireAnyPerm(...)` 保护。

当前仍是“请求携带用户标识”的轻量鉴权模式，尚未形成完整的登录会话、JWT、CSRF 防护和网关认证闭环。生产环境必须在反向代理或统一身份层补齐这一边界，不能仅依赖浏览器端隐藏菜单。

### 6.3 JSON 数据访问

`backend/db.js` 提供每表内存缓存、表级 FIFO 写互斥、临时文件原子重命名、异步大文件写盘和关键表 `.bak` 恢复。关键鉴权表和 `materials` 会保留备份，解析失败或空表时尝试自愈。

该方案适合单机、单容器和中小规模数据；多实例部署前应迁移到 SQLite/PostgreSQL，并增加分布式锁、统一缓存和对象存储。

## 7. AI 助手方案

### 7.1 请求链路

```text
dashboard / ai-assistant / chat-widget
        │
        ▼
POST /api/chat
        │
        ├─ 从 system_settings 读取 AI 配置
        ├─ 组装业务上下文和用户消息
        ├─ 调用 OpenAI-compatible /chat/completions
        ├─ 解析并保存行动项
        └─ 返回 reply、action_items、model
```

当前实际验证过的配置口径为：API Base `https://open.bigmodel.cn/api/paas/v4`，模型 `glm-5.2`。API Key 只保存在运行时设置中，本文不记录、不提交、不输出。

### 7.2 已修复问题

- AI 配置读取统一使用 `system_settings`，与设置页面一致。
- 外部请求使用 Node 22 原生 `globalThis.fetch`。
- 外部成功响应返回实际计算得到的 `actionItems`。
- 修复图标 MutationObserver 反复挂载 SVG 导致 AI 页面崩溃的问题。

AI 故障排查顺序：确认容器健康；确认设置中的 API Base、模型和 Key；检查 `/api/chat` 状态、`model` 和 `action_items`；外部模型失败时保留可理解的错误提示，不让前端崩溃。回归脚本为 `scripts/ai-config-regression.test.js`。

## 8. 订单分析库方案

订单分析库包含四条主线：

1. 订单审核：待审核、通过、驳回和审核留痕。
2. 计划成本：BOM × 物料单价，并叠加人工费率与费用口径形成成本快照。
3. 同类订单比对：按产品编码、客户和 BOM 构成识别相似订单并逐项比较。
4. 计划与实际：物料、人工和费用按订单号归集并标识超支。

SPC/ERP 多级 BOM 优先通过外部接口获取，再转换为本地成本树；原始 BOM 树按 BOM 编号保留 30 分钟内存缓存；物料价格和审核工价在成本转换时实时取本地库。

订单分析报表 `/api/order-analysis/report/summary` 使用短 TTL 聚合缓存。性能回归脚本验证重复请求必须返回 `X-EBMS-Cache: HIT`，且缓存命中小于 1 秒。已有验证记录中，物料看板统计接口首次请求约 280ms，重复请求约 7ms；该数字不是所有数据规模下的 SLA 承诺。

## 9. 数据、备份与恢复

### 9.1 数据分类

- 业务数据：客户、询价、报价、订单、项目、物料、供应商、采购、费用、人工、SOP 和消息。
- 系统数据：用户、角色、权限、组织、岗位、数据范围和 `system_settings`。
- 运行时数据：`uploads/`、同步结果、缓存、备份文件和日志。

### 9.2 备份要求

升级前至少备份 `database/` 和 `uploads/`，同时记录当前 Git commit、Docker 镜像版本和部署时间。启动快照、`.bak` 和物料自愈只属于故障兜底，不能替代离线备份、异地备份和恢复演练。

物料和订单 BOM 明细可能达到数十 MB 甚至数百 MB。为避免全量写盘阻塞事件循环，物料自检、核价同步、AI 自动引擎和外部同步等周期任务默认关闭；需要启用时设置 `ENABLE_PERIODIC_TASKS=1`，并在低峰期观察日志、响应时间和磁盘空间。

## 10. Docker 部署方案

### 10.1 构建与启动

```powershell
docker compose up -d --build
docker compose ps
docker compose logs --tail=100
```

访问：`http://localhost:3010/`；停止：`docker compose down`。

### 10.2 容器特性

- Node 22 Alpine 基础镜像。
- 使用 `tini` 作为 PID 1。
- 使用非 root 用户 `app` 运行服务。
- 健康检查访问 `http://127.0.0.1:3010/index.html`。
- `database` 和 `uploads` 通过宿主机目录持久化。
- `restart: unless-stopped`，时区为 `Asia/Shanghai`。
- 可选环境变量：`PORT`、`NODE_ENV`、`TZ`、`ENABLE_PERIODIC_TASKS`、`HTTPS_PFX_PASSPHRASE`。

### 10.3 升级流程

1. 备份 `database/` 和 `uploads/`。
2. 检查代码差异和配置变更。
3. 执行 `docker compose down` 后再 `docker compose up -d --build`。
4. 检查 `docker compose ps` 为 healthy，并查看最近日志。
5. 回归登录、首页、询价、客户、订单分析、AI、消息、设置、项目、物料、报价预览和导入导出。

## 12. 风险与后续路线

### P0：生产前必须处理

1. 将订单分析和外部服务中可能存在的硬编码凭证迁移到环境变量或受保护设置，并轮换已有凭证。
2. 在反向代理或统一身份服务中补齐真实登录会话，禁止生产环境仅凭 `x-user-id` 识别身份。
3. 收紧生产 CORS、上传文件类型、文件大小、错误信息和日志敏感字段。
4. 建立可恢复的数据库/上传文件备份并完成恢复演练。

### P1：稳定性与可维护性

1. 为订单分析报表、BOM 树和大列表建立按数据规模分级的性能基线。
2. 将高频 JSON 表逐步迁移到事务型数据库，同时保持现有 API 契约。
3. 为 ERP/SPC 接口增加超时、重试、熔断、密钥轮换和调用审计。
4. 将根目录 `frontend/` 作为唯一发布源，持续清理历史镜像误修改风险。

### P2：经营智能化

1. 将 S&OP 指标、风险事件、预测结果和 Action 统一为可追踪对象。
2. 引入目标上下文、指标可信度和结果验证字段，避免 AI 生成没有业务依据的行动。
3. 在权限和数据质量稳定后，再建设企业 Memory、岗位 Skills 和可控自动执行。

## 13. 交付结论

当前版本适合作为单机或单容器部署的 EBMS 业务平台基线：业务域覆盖较完整，Docker 运行路径明确，AI、图标系统、数据写入和聚合缓存已有针对性修复与回归脚本。正式生产化前，应优先完成身份认证、密钥治理、备份恢复和外部接口安全加固，再扩大自动化调度和 AI 闭环范围。
